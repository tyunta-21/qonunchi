# ADR-0001. SQLite FTS5 (BM25) вместо векторной базы

**Статус:** принято

## Контекст

Нужно искать по ~32 000 статей на двух языках (узбекская латиница и русский). Типичный RAG-проект берёт векторную БД (Pinecone, Chroma, pgvector) и эмбеддинги. Но юридические вопросы часто держатся на точных словах и числах: «статья 217», «BHM», «ежегодный отпуск». Эмбеддинги такие совпадения размывают, а для узбекского языка качественных моделей эмбеддингов мало.

## Решение

Индекс — SQLite с виртуальными таблицами FTS5 и ранжированием BM25. Веса полей: заголовок статьи 4,0, название акта 2,5, текст 1,0. Нормализация (апострофы, регистр, ё→е) и префиксный стемминг в `app/textnorm.py` одинаковы при индексации и при поиске. Смысловую близость даёт не вектор, а переписывание запроса LLM ([ADR-0002](0002-llm-query-rewriting.md)) и вторичное ранжирование в Python.

## Последствия

- ➕ Вся база — один файл `laws.db`, никакого отдельного сервера, деплой копированием файла.
- ➕ Поиск занимает миллисекунды и полностью воспроизводим.
- ➕ Тот же индекс обслуживает и обычный поиск на сайте с подсветкой (`snippet()`), и ИИ.
- ➖ Синонимы без переписывания не находятся.
- ➖ SQLite — один писатель; для нашего режима (запись только при сборке) это не проблема.
- Путь развития: добавить эмбеддинги как ещё один сигнал в формулу ранжирования, не меняя остальной системы.
